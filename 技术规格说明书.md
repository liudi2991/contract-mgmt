## 3. 数据库设计

### 3.1 设计原则

- 字符集：`utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`。
- 引擎：InnoDB。
- 主键：所有表使用 `BIGINT UNSIGNED AUTO_INCREMENT`。
- 通用字段：`created_at`、`created_by`、`updated_at`、`updated_by`、`deleted`（逻辑删除 0/1）。
- 金额：`DECIMAL(18,2)`，避免浮点精度问题。
- 日期：`DATE` 或 `DATETIME`，禁用 `TIMESTAMP`（避免 2038 问题）。
- 索引：所有外键字段建立索引；常用查询条件建复合索引。

### 3.3 表结构 DDL

#### 3.3.1 `sys_user` 用户表

```sql
CREATE TABLE `sys_user` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `username`      VARCHAR(50)  NOT NULL                        COMMENT '登录账号',
  `password_hash` VARCHAR(100) NOT NULL                        COMMENT 'bcrypt 哈希',
  `name`          VARCHAR(50)  NOT NULL                        COMMENT '姓名',
  `email`         VARCHAR(100) DEFAULT NULL,
  `role`          VARCHAR(20)  NOT NULL                        COMMENT 'SALES / ADMIN',
  `status`        TINYINT      NOT NULL DEFAULT 1              COMMENT '1=启用 0=停用',
  `must_change_pwd` TINYINT    NOT NULL DEFAULT 1              COMMENT '首次登录强制改密',
```

#### 3.3.2 `contract` 合同表

```sql
CREATE TABLE `contract` (
  `id`               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `contract_no`      VARCHAR(32)  NOT NULL                     COMMENT '合同编号 HT-YYYY-XXXX',
  `name`             VARCHAR(100) NOT NULL                     COMMENT '合同名称',
  `customer_name`    VARCHAR(100) NOT NULL                     COMMENT '客户名称（自由文本）',
  `amount`           DECIMAL(18,2) NOT NULL                    COMMENT '合同总金额',
  `currency`         VARCHAR(8)   NOT NULL DEFAULT 'CNY',
  `sign_date`        DATE         NOT NULL                     COMMENT '签订日期',
  `effective_date`   DATE         NOT NULL                     COMMENT '生效日期',
  `expire_date`      DATE         NOT NULL                     COMMENT '到期日期',
  `owner_id`         BIGINT UNSIGNED NOT NULL                  COMMENT '负责人',
  `status`           VARCHAR(20)  NOT NULL DEFAULT 'EXECUTING' COMMENT 'EXECUTING/COMPLETED/EXPIRED/VOIDED',
  `void_reason`      VARCHAR(500) DEFAULT NULL,
  `paid_amount`      DECIMAL(18,2) NOT NULL DEFAULT 0          COMMENT '已回款金额（冗余）',
  `remaining_amount` DECIMAL(18,2) NOT NULL DEFAULT 0          COMMENT '应收余额（冗余）',
  `remark`           VARCHAR(500) DEFAULT NULL,
  `created_at`       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `created_by`       BIGINT       NOT NULL,
  `updated_at`       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `updated_by`       BIGINT       NOT NULL,
  `deleted`          TINYINT      NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_contract_no` (`contract_no`, `deleted`),
  KEY `idx_owner`     (`owner_id`,    `sign_date`),
  KEY `idx_customer`  (`customer_name`),
  KEY `idx_status`    (`status`,      `expire_date`),
  KEY `idx_sign_date` (`sign_date`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='合同主表';
```

> **设计说明**：`paid_amount` 与 `remaining_amount` 为冗余字段，由回款核销后异步更新，避免每次查询都聚合 `payment` 表。统计报表直接读取，列表展示性能更优。

## 4. 接口设计

### 4.1 接口规范

- **风格**：RESTful + JSON。
- **路径前缀**：`/api/v1`。
- **认证**：HTTP Header `Authorization: Bearer <JWT>`。
- **字符编码**：UTF-8。
- **时间格式**：ISO 8601 `yyyy-MM-dd` 或 `yyyy-MM-dd HH:mm:ss`，时区固定 `Asia/Shanghai`。
- **金额格式**：JSON 中使用字符串避免精度问题，例如 `"amount": "10000.00"`。

### 4.2 统一响应结构

```json
{
  "code": 0,
  "message": "ok",
  "data": { ... },
  "traceId": "a1b2c3d4"
}
```

- `code = 0`：成功；非 0 为业务/系统错误。

## 5. 关键业务逻辑设计

### 5.1 合同编号生成

**算法**：

1. 读取 `sys_param` 中的 `contract.no.prefix`、`contract.no.serial_length`、`contract.no.reset_yearly`。
2. 取当前年份 `YYYY`。
3. 在 Redis 中维护键 `contract:no:seq:{YYYY}`，使用 `INCR` 原子自增获取流水号。
4. 流水号按位数补零，拼接为 `{prefix}-{YYYY}-{serial}`。
5. 落库后在 `contract.contract_no` 唯一索引兜底；若冲突（极端情况）则 INCR 重试一次。
6. 应用启动时校对 Redis 计数：`SELECT MAX(SUBSTRING(...)) FROM contract WHERE YEAR(sign_date)=YYYY`，写入 Redis 防止丢失。

```java
public String generateContractNo() {
    String prefix = sysParam.get("contract.no.prefix");
    int length    = sysParam.getInt("contract.no.serial_length");
    int year      = LocalDate.now().getYear();
    String key    = "contract:no:seq:" + year;
    long seq      = redisTemplate.opsForValue().increment(key);
    return String.format("%s-%d-%0" + length + "d", prefix, year, seq);
}
```

### 5.2 回款核销算法

**入口**：登记实际回款（`POST /payments`）或修改/删除回款。

**事务边界**：单一事务内完成 `payment` 写入 + `payment_plan_item` 更新 + `contract` 冗余字段更新。

**算法（新增回款）**：

```
输入：contractId, planItemId(可空), amount
1. SELECT ... FOR UPDATE 锁定 contract 行
2. 校验 contract.status != VOIDED
3. INSERT payment 行
4. IF planItemId != null:
       记 settle(planItemId, amount)
   ELSE:
       remaining = amount
       FOR item IN (按 planned_date asc 的未结清期次):
           gap = item.planned_amount - item.received_amount
           applied = min(gap, remaining)
           settle(item.id, applied)
           remaining -= applied
           IF remaining == 0: break
       IF remaining > 0:
           // 超额回款，挂在合同上不分摊到期次（记入 payment 但不更新 plan_item）
5. UPDATE contract
       paid_amount = paid_amount + amount
       remaining_amount = amount - paid_amount
6. 触发状态机判定（见 5.4）
7. COMMIT
```

`settle(planItemId, delta)`：

```
plan_item.received_amount += delta
IF received_amount >= planned_amount: status = SETTLED
ELSE IF received_amount > 0:           status = PARTIAL
ELSE:                                   status = UNPAID
```

**算法（删除回款）**：反向操作，按"先核销的最后回退"原则，从对应 plan_item 上减去金额并重算状态。

### 5.3 回款计划生成

```
输入：contractId, mode, periods[]
mode = MANUAL:  直接落库
mode = RATIO:   periods = [{ratio, intervalDays}, ...]
                amount_total = contract.amount
                累加 = 0
                for i in 0..n-2:
                    amount_i = round(amount_total * ratio_i, 2)
                    累加 += amount_i
                amount_last = amount_total - 累加     # 兜底防止累计误差
                日期 = sign_date + 累计 intervalDays
落库后做总额一致性校验：SUM(planned_amount) == contract.amount，否则回滚。
```

### 5.4 合同状态自动流转

**主动触发**：登记/删除回款、编辑合同 → 立即判定。

**被动触发**：每日 `00:30` 定时任务全表扫描，对 `EXECUTING` 合同做判定。

**判定规则**：

```
if status == VOIDED: 不变
elif remaining_amount == 0 and today >= expire_date: → COMPLETED
elif today > expire_date and remaining_amount > 0:   → EXPIRED
else:                                                 → EXECUTING
```

> COMPLETED 后允许回退到 EXECUTING（例如删除某笔回款使余额重新 > 0）。

### 5.5 到期提醒

**定时任务**：`@Scheduled(cron = "0 0 8 * * *")` 每日 08:00。

```
读取 sys_param "contract.remind.days" 得 [30, 15, 7, 1]
for d in days:
    target = today + d days
    SELECT id, owner_id, contract_no, name
      FROM contract
     WHERE status = 'EXECUTING' AND expire_date = target
    for each row:
        INSERT INTO notification (user_id=owner_id, type='CONTRACT_EXPIRING', ...)
```

幂等：当日同一 `(user_id, type, contract_id, expire_date)` 唯一约束（应用层校验，避免重复推送）。

### 5.6 文件上传与下载

**上传**：

1. 前端调用 `POST /contracts/{id}/attachments`，`multipart/form-data`。
2. 后端校验：MIME 类型白名单、单文件大小、单合同总数。
3. 计算 MD5，生成对象 key：`contract/{contractId}/{uuid}-{原文件名}`。
4. 上传至 MinIO（bucket = `contract-mgmt`）。
5. 写 `attachment` 元数据。

**下载**：

1. 前端调用 `GET /attachments/{id}/url`。
2. 后端做权限校验（销售员仅能访问自己合同的附件）。
3. 通过 MinIO SDK 生成 15 分钟有效的预签名 URL，返回前端。
4. 前端用该 URL 直接走 MinIO 下载/预览，**不经过后端转发**，减轻后端压力。

**MIME 白名单**：

```
application/pdf, application/msword,
application/vnd.openxmlformats-officedocument.wordprocessingml.document,
application/vnd.ms-excel,
application/vnd.openxmlformats-officedocument.spreadsheetml.sheet,
image/jpeg, image/png
```

### 5.7 全量数据导出

**流程**：

```
1. 前端调用 GET /contracts/export 等
2. 后端在 Redis 中检查并自增计数 export:count:{userId}:{yyyyMMdd}
   超过 sys_param "export.daily_limit_per_admin" 返回 50001 错误
3. 写 export_record(status=RUNNING)
4. 判断预估行数 < 10 万：同步导出，EasyExcel 流式写入并返回文件
       行数 ≥ 10 万：投递到本地异步任务队列（Spring @Async + 线程池）
5. 完成后：
   - 计算文件 MD5，更新 export_record(status=SUCCESS, file_md5, finished_at)
   - 写 audit_log
   - 异步导出时推送 notification(type=EXPORT_DONE, target_url=下载链接)
```

### 5.8 操作日志记录

**实现方式**：自定义注解 + Spring AOP。

```java
@AuditLog(module = "CONTRACT", action = "UPDATE", targetIdSpEL = "#id")
public ContractVO update(Long id, ContractUpdateDTO dto) { ... }
```

AOP 切面在方法成功返回后异步写入 `audit_log`（独立线程池，避免拖慢业务）。

**变更前/后值**：用 Jackson 序列化为 JSON，金额转字符串避免精度问题。

## 7. 安全设计

### 7.1 认证

- **方式**：用户名 + 密码 + JWT。
- **JWT 设置**：
  - 算法：HS256
  - 有效期：2 小时
  - Claims：`uid`、`username`、`role`、`iat`、`exp`
  - 密钥：从环境变量注入，长度 ≥ 32 字节
- **续期**：客户端在 401 前 10 分钟调用 `/auth/refresh`（如启用），或简单做法："活跃 = 重新登录"，不实现刷新令牌。
- **登出**：将 token 加入 Redis 黑名单 `jwt:blacklist:{jti}`，TTL 等于剩余有效期。
- **密码哈希**：`BCryptPasswordEncoder(strength=10)`。
- **登录锁定**：Redis 键 `login:fail:{username}`，失败 5 次锁定 10 分钟。

### 7.2 授权

- **角色**：`SALES`、`ADMIN`，存于 JWT 与数据库。
- **方法级**：`@PreAuthorize("hasRole('ADMIN')")`。
- **数据级**：在 Service 层统一注入"当前用户"，对查询追加 `WHERE owner_id = :currentUserId`（管理员跳过）；对更新先校验所有权。

```java
public ContractVO get(Long id) {
    Contract c = mapper.selectById(id);
    securityHelper.assertCanRead(c);     // 销售员只能读自己 / 管理员任意
    return convert(c);
}
```

### 7.3 数据安全

- **传输**：Nginx 配置 TLS 1.2/1.3，HSTS。
- **存储**：密码 bcrypt；数据库主机层面磁盘加密由部署方负责。
- **附件**：MinIO bucket 设为 private；下载走预签名 URL（15 min 有效）。
- **敏感数据**：当前需求未明确字段脱敏，**所有金额对所有登录用户可见**（角色权限范围内）。

### 7.4 防越权

- **横向越权**：所有对资源的写操作均做"是否本人或管理员"校验。
- **纵向越权**：路由与按钮基于 `role` 渲染；后端复核。
- **测试**：QA 阶段必跑越权测试用例（用销售员 token 访问他人合同接口）。

### 7.5 限流与防刷

| 接口                    | 策略                                      |
| ----------------------- | ----------------------------------------- |
| /auth/login             | 单 IP 每分钟 10 次；单账号失败 5 次锁定   |
| /exports/*              | 单用户每日 N 次（来自 sys_param）         |
| 全量接口                | 单 token 每秒 20 次（Bucket4j 令牌桶）    |

实现：自定义 Spring 拦截器 + Redis（Bucket4j-Redis 或自实现 INCR + EXPIRE）。

### 7.6 其他

- 启用 `Content-Security-Policy`、`X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`。
- 关闭 Spring Boot Actuator 公网暴露；监控端口绑定内网。
- SQL 注入：MyBatis 全部使用参数化（`#{}` 不用 `${}`）。
- XSS：前端使用 Vue 模板默认转义；富文本场景本期不存在。

## 8. 性能设计

### 8.1 数据库优化

- 关键查询全部走索引，禁止全表扫描。
- 合同列表查询走 `idx_owner + sign_date` 或 `idx_status + expire_date`。
- 聚合统计避开实时 `SUM`：使用 `contract.paid_amount` 冗余字段。
- 分页用 `LIMIT offset, size`，offset 大时改用"基于游标"（按 id 范围）—本期数据量未到这一步。

### 8.2 缓存

| 数据         | Key                              | TTL    |
| ------------ | -------------------------------- | ------ |
| 系统参数     | `sys:param:{key}`                | 5 min  |
| 用户基本信息 | `user:{id}`                      | 30 min |
| 合同编号流水 | `contract:no:seq:{year}`         | 永久   |
| 登录失败计数 | `login:fail:{username}`          | 10 min |
| 令牌黑名单   | `jwt:blacklist:{jti}`            | = TTL  |
| 导出限频     | `export:count:{userId}:{date}`   | 至当日 24:00 |

修改系统参数后主动 evict 缓存。

### 8.3 异步与定时

| 任务                | 触发           | 执行体              |
| ------------------- | -------------- | ------------------- |
| 合同状态扫描        | 每日 00:30     | 单 SQL UPDATE 批处理|
| 到期提醒推送        | 每日 08:00     | 批量 INSERT notification |
| 备份                | 每日 02:00     | mysqldump + minio mc |
| 大数据导出          | 用户触发       | @Async 线程池 (core=2, max=4) |
| 操作日志写入        | 业务方法返回后 | @Async 线程池 (core=2, max=8, queue=1000) |

### 8.4 性能指标对应

| 需求指标                | 实现保障                                                   |
| ----------------------- | ---------------------------------------------------------- |
| 列表页 P95 ≤ 2s         | 索引 + 分页 + 不做实时聚合                                 |
| 详情页 P95 ≤ 1.5s       | 主键查询 + 关联表 ≤ 4 张，附件元数据单独懒加载             |
| 报表 ≤ 5s               | 单表聚合 + 数据量小；可加入"小时级"物化（本期不必）        |
| 50 并发                 | Tomcat 默认线程池 200 即可承载；Redis/MySQL 连接池足量配置 |

### 9.4 备份策略

| 数据         | 频率     | 方式                                | 保留期 |
| ------------ | -------- | ----------------------------------- | ------ |
| MySQL        | 每日 02:00 | `mysqldump --single-transaction` → 本地 → rsync 至 NAS | 30 天 |

| 配置 & 脚本  | 每次发布 | git 仓库                            | 永久   |

恢复演练：每季度一次，验证从备份完全重建系统。

### 9.5 监控与告警

- **健康检查**：`GET /actuator/health` 暴露在内网。
- **运维监控（建议）**：Uptime Kuma 或 Prometheus + Node Exporter + MySQL Exporter + Grafana。
- **告警通道**：邮件（由开发团队配置邮件服务）。
- **关键告警**：
  - API 错误率 > 1%（5 分钟窗口）
  - MySQL 连接数 > 80%
  - 磁盘使用率 > 80%
  - 附件存储用量 > 80%

### 9.6 日志规范

- 应用日志：JSON 格式，按天滚动，保留 30 天，写入 `/var/log/contract-mgmt/`。
- 关键字段：`traceId`、`userId`、`module`、`action`、`durationMs`。
- 错误日志单独文件 `error.log`，便于排障。

### 9.7 发布流程（CI/CD 建议）

```
git push → GitLab CI / GitHub Actions
  ├── 后端：mvn test → docker build → push to registry
  ├── 前端：npm ci → npm run build → 产物推送 OSS/镜像
  └── 部署：SSH 到服务器执行 docker compose pull && up -d
```

灰度策略：本期单机部署不做灰度；通过功能开关（Feature Flag）控制新功能上线。

## 10. 编码规范

### 10.1 Java（参考阿里规范）

- 包、类、方法命名遵循驼峰；常量全大写下划线。
- DTO 后缀 `DTO`，VO 后缀 `VO`，Entity 不加后缀。
- Service 接口与实现拆分（`XxxService` / `XxxServiceImpl`）。
- 所有公开方法必须有 Javadoc。
- 禁止在 Controller 中写业务逻辑；事务边界在 Service。
- 单元测试覆盖核心 Service ≥ 70%。
- 静态分析：SonarQube / SpotBugs 接入 CI。

### 10.2 TypeScript / Vue

- 组件名 PascalCase；文件名同组件名。
- API 请求统一通过 `src/api/` 调用，禁止在组件内直接 axios。
- 使用 `<script setup lang="ts">`；props/emits 必须声明类型。
- ESLint + Prettier 在 commit 前 husky 强制执行。

### 10.3 Git

- 分支策略：`main`（生产）、`develop`（集成）、`feature/*`、`fix/*`。
- 提交消息：Conventional Commits（`feat:`、`fix:`、`refactor:` ...）。
- PR 必须 ≥ 1 人 Review + CI 通过方可合并。

## 12. 风险与对策

| 风险                                          | 影响                       | 概率 | 对策                                                                |
| --------------------------------------------- | -------------------------- | ---- | ------------------------------------------------------------------- |
| 客户名称自由文本导致统计失真                  | 报表准确性下降             | 高   | 销售员录入培训 + 名称建议（输入时模糊提示已有名称）；V2 引入字典    |
| 单机部署故障导致全员不可用                    | 业务中断                   | 中   | 每日备份 + 4 小时内恢复演练；后续可加从库或迁移到云                 |
| 附件磁盘写满                                  | 上传失败                   | 中   | 80% 告警 + 运维预案；MinIO 数据目录单独挂盘易扩容                   |
| 合同冗余字段（paid/remaining）与流水不一致    | 数据不一致                 | 中   | 事务内同步更新；每日定时任务对账，发现差异告警                      |
| 大量日志影响 audit_log 查询                   | 日志查询慢                 | 低   | 按月分区 / 归档到冷存储；2 年外的日志可归档                         |
| MinIO 升级或迁移                              | 附件不可访问               | 低   | 使用 S3 兼容接口，便于切换；备份桶始终独立                          |
| 开发人员误删生产数据                          | 数据丢失                   | 中   | 生产库严格只读账号 + 双人复核；逻辑删除而非物理删除                 |
